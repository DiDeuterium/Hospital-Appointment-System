# 医院预约挂号系统新增功能规划

## 一、规划目标

本功能规划基于 `docs/new/升级方案-数据库设计.md` 中的 9 表数据库设计，新增功能仍然围绕“挂号预约”主题展开。

新增功能主要服务于以下目标：

1. 让科室、医生、排班支持“停用/停诊”而不是物理删除。
2. 让医生可以主动发起排班变更申请。
3. 让管理员可以审核排班变更，并由系统自动调整排班。
4. 让患者端能看到更完整的医生信息、公告信息和预约排队号。
5. 让管理员账号从配置文件迁移到数据库中统一管理。
6. 增加挂号费模拟支付流程，让挂号流程更完整，但不调用真实支付接口。

## 二、患者端新增功能

### 1. 医生信息展示增强

对应数据库字段：

```text
doctor.avatar_url
doctor.specialty
doctor.status
```

新增功能：

1. 医生列表页展示医生头像、职称、擅长领域摘要。
2. 医生详情页展示完整擅长领域、所属科室、头像、可预约排班。
3. 患者端只展示 `status = 1` 的医生。
4. 历史预约详情仍然可以展示已停用医生的信息。
5. 停用医生不能登录医生端。

头像处理建议：

```text
avatar_url 只保存图片访问路径，不保存图片二进制内容。
例如：/avatars/doctor-1.jpg
```

### 2. 科室状态过滤

对应数据库字段：

```text
department.status
```

新增功能：

1. 患者端科室列表只展示 `status = 1` 的科室。
2. 停用科室下的医生和排班不再进入患者可预约入口。
3. 患者历史预约仍然可以通过外键查询到原科室信息。

### 3. 排班状态与挂号费展示

对应数据库字段：

```text
schedule.status
schedule.fee
```

新增功能：

1. 排班卡片展示挂号费。
2. 患者只能预约 `status = 1` 且 `rest_quota > 0` 的排班。
3. `status = 0` 的停诊排班不展示在普通可预约列表中。


### 4. 预约排队号展示

对应数据库字段：

```text
appointment.queue_number
```

新增功能：

1. 挂号成功页展示排队号。
2. 我的预约列表展示排队号。
3. 预约详情页展示排队号、预约状态、创建时间。
4. 同一排班下排队号不能重复，由后端生成并保证唯一。

### 5. 挂号费模拟支付

对应数据库表和字段：

```text
payment_record
schedule.fee
```

新增功能：

1. 患者预约成功后，系统生成一条挂号费待支付记录。
2. 支付金额来自对应排班的 `schedule.fee`。
3. 患者在预约成功页或预约详情页点击“模拟支付”按钮。
4. 点击后不调用真实支付接口，系统直接将 `payment_record.pay_status` 更新为 `1 已支付`。
5. 支付成功后记录 `pay_time`。
6. 支付状态只表示挂号费模拟支付状态，不改变 `appointment.status`。
7. 已支付记录不能重复支付。

支付状态：

```text
0 待支付
1 已支付
2 已关闭
```

### 6. 取消预约原因

对应数据库字段：

```text
appointment.cancel_reason
appointment.update_time
```

新增功能：

1. 患者取消预约时可以填写取消原因。
2. 取消原因可以选填，默认可为空。
3. 预约详情页展示取消原因和最后更新时间。
4. 已取消、已就诊、已过期预约不能重复取消。

### 7. 系统公告查看

对应数据库表：

```text
sys_notice
```

新增功能：

1. 患者首页展示置顶公告和最新公告。
2. 公告列表支持查看全部已发布公告。
3. 公告详情展示标题、正文、发布时间。
4. 只展示 `status = 1` 的公告。

## 三、医生端新增功能

### 1. 我的排班状态展示

对应数据库字段：

```text
schedule.status
```

新增功能：

1. 医生排班列表展示出诊状态：正常、停诊。
2. 医生排班列表展示总号源、剩余号源、已预约人数。
3. 停诊排班仍可查看，但不能继续被患者预约。

### 2. 发起停诊申请

对应数据库表：

```text
schedule_change_request
```

新增功能：

1. 医生可以对自己的某条排班发起停诊申请。
2. 发起停诊申请时必须填写申请原因。
3. 发起停诊申请前，系统检查该排班是否存在有效预约。
4. 如果存在 `appointment.status = 1` 的有效预约，禁止提交停诊申请。
5. 如果不存在有效预约，允许提交申请，申请状态为 `1 待审核`。

提交前校验：

```sql
SELECT COUNT(*)
FROM appointment
WHERE schedule_id = ?
  AND status = 1;
```

### 3. 发起修改排班申请

对应数据库字段：

```text
schedule_change_request.target_work_date
schedule_change_request.target_shift
schedule_change_request.target_total_quota
```

新增功能：

1. 医生可以申请修改排班日期、时段、总号源。
2. 一次申请可以同时修改日期、时段和总号源。
3. 修改排班申请至少填写一个目标字段。
4. 如果申请修改日期或时段，要检查目标日期和目标时段是否已有该医生的其他排班。
5. 如果该排班已有有效预约，不允许修改日期和时段。
6. 如果该排班已有有效预约，仍允许调整总号源，但新总号源不能小于已预约人数。

### 4. 我的申请列表

对应数据库表：

```text
schedule_change_request
```

新增功能：

1. 医生可以查看自己发起的排班变更申请。
2. 列表展示申请类型、原排班信息、目标修改内容、申请原因、审核状态、申请时间。
3. 详情页展示审核管理员、审核时间、审核意见。
4. 待审核申请可以撤回。
5. 已通过、已驳回、已撤回申请不能再次撤回。

说明：

```text
schedule_change_request 不保存 doctor_id。
医生查看自己的申请时，通过 schedule_id 关联 schedule.doc_id 查询。
```

### 5. 患者名单增强

对应数据库字段：

```text
appointment.queue_number
appointment.status
```

新增功能：

1. 医生查看某排班患者名单时，按排队号排序。
2. 患者名单展示排队号、患者姓名、性别、手机号、预约状态。
3. 医生确认就诊后，预约状态更新为 `3 已就诊`。

### 6. 医生个人资料维护

对应数据库字段：

```text
doctor.avatar_url
doctor.specialty
doctor.password
```

新增功能：

1. 医生可以查看自己的个人资料。
2. 医生可以修改自己的头像 URL。
3. 医生可以修改自己的擅长领域。
4. 医生可以修改自己的登录密码。
5. 医生不能修改姓名、性别、职称、所属科室、账号状态等组织身份信息。

权限边界：

```text
医生本人可以维护个人展示信息：头像、擅长领域、密码。
管理员维护组织管理信息：姓名、性别、职称、所属科室、状态、初始密码。
```

## 四、管理员端新增功能

### 1. 管理员账号数据库化

对应数据库表：

```text
admin_user
```

新增功能：

1. 管理员登录改为从 `admin_user` 表查询。
2. 管理员密码使用 BCrypt 哈希存储。
3. 只允许 `status = 1` 的管理员登录。
4. `status = 0` 的管理员禁止登录。
5. 后续可增加管理员新增、停用、重置密码功能。

当前配置文件中的管理员账号：

```text
admin / admin123
```

应迁移为 `admin_user` 表中的初始化数据。

### 2. 科室启用/停用

对应数据库字段：

```text
department.status
```

新增功能：

1. 管理员可以启用或停用科室。
2. 停用科室不从数据库删除。
3. 停用科室后，患者端不再展示该科室。
4. 若科室下存在未来有效排班，停用前应给出提示。

### 3. 医生信息增强管理

对应数据库字段：

```text
doctor.avatar_url
doctor.specialty
doctor.status
```

新增功能：

1. 管理员新增/编辑医生时维护头像 URL。
2. 管理员新增/编辑医生时维护擅长领域。
3. 管理员可以启用或停用医生。
4. 停用医生不从数据库删除。
5. 停用医生后，患者端不再展示该医生的新排班入口。
6. 停用医生后，该医生不能登录医生端。
7. 管理员可以修改医生的组织管理信息，包括姓名、性别、职称、所属科室、状态和初始密码。
8. 医生本人也可以维护头像和擅长领域，但不能修改组织管理信息。

### 4. 排班管理增强

对应数据库字段：

```text
schedule.fee
schedule.status
```

新增功能：

1. 管理员发布排班时维护挂号费。
2. 管理员排班列表展示排班状态。
3. 管理员可以查看正常排班和停诊排班。
4. 管理员手动修改排班时仍需遵守号源约束：

```text
0 <= rest_quota <= total_quota
```

### 5. 排班变更申请审核

对应数据库表：

```text
schedule_change_request
```

新增功能：

1. 管理员查看所有待审核排班变更申请。
2. 管理员可以按状态筛选申请：待审核、已通过、已驳回、已撤回。
3. 管理员可以查看申请详情，包括原排班、申请类型、目标修改内容、申请原因。
4. 管理员可以通过或驳回申请，并填写审核意见。
5. 审核通过后，系统自动修改 `schedule` 表。
6. 审核操作必须防止多个管理员同时处理同一申请。

并发控制规则：

```sql
UPDATE schedule_change_request
SET
    status = 2,
    audit_admin_id = ?,
    audit_time = NOW(),
    audit_remark = ?
WHERE request_id = ?
  AND status = 1;
```

影响行数为 1 表示审核成功；影响行数为 0 表示申请已被其他管理员处理。

### 6. 停诊申请审核规则

新增功能：

1. 管理员审核通过停诊申请前，再次检查该排班是否存在有效预约。
2. 如果存在 `appointment.status = 1` 的有效预约，禁止通过。
3. 如果不存在有效预约，审核通过后自动执行：

```text
schedule.status = 0
```

### 7. 修改排班申请审核规则

新增功能：

1. 管理员审核通过修改排班申请前，再次执行业务校验。
2. 修改日期或时段时，检查目标日期和目标时段是否已有同医生排班。
3. 已有有效预约时，禁止修改日期和时段。
4. 修改总号源时，新总号源不能小于已预约人数。
5. 审核通过后，系统根据非空目标字段自动更新 `schedule`。

### 8. 支付记录查看

对应数据库表：

```text
payment_record
```

新增功能：

1. 管理员可以查看挂号费模拟支付记录。
2. 列表展示预约单号、患者姓名、医生、科室、排班日期、金额、支付状态、支付时间。
3. 管理员可以按支付状态筛选：待支付、已支付、已关闭。
4. 管理员可以按支付时间范围、科室、医生、排班日期、排班时段、预约单号、支付记录号筛选。
5. 列表中可以展示患者姓名和手机号后四位用于人工核对，但不以患者姓名作为主要筛选条件。
6. 本系统不处理真实退款，已支付后取消预约只保留支付记录用于演示和查询。

### 9. 系统公告管理

对应数据库表：

```text
sys_notice
```

新增功能：

1. 管理员可以新增公告。
2. 管理员可以编辑公告标题、正文、是否置顶、发布状态。
3. 管理员可以下线公告。
4. 管理员公告列表支持按状态筛选。
5. 患者端只展示已发布公告。

## 五、实现优先级建议

### 第一优先级

1. 数据库字段升级：`status`、`avatar_url`、`specialty`、`fee`、`queue_number`、`cancel_reason`、`update_time`，并新增 `payment_record` 表。
2. 管理员账号迁移到 `admin_user` 表。
3. 患者端展示医生头像、擅长领域、挂号费、排队号。
4. 预约创建时生成排队号和待支付记录。
5. 患者端支持挂号费模拟支付。

### 第二优先级

1. 医生端排班变更申请。
2. 管理员端排班变更审核。
3. 审核通过后自动修改排班。
4. 停诊申请和修改排班申请的业务校验。
5. 医生个人资料维护。

### 第三优先级

1. 系统公告管理。
2. 患者端公告展示。
3. 科室和医生启用/停用的完整前端管理。
4. 管理员端支付记录查看。
